## S-X-01 · L1/L2 导航记忆与结果保留

### 背景

用户在基础视角集成页的「体检」区块与「测试 · Ping」间来回对比。

### 步骤

1. 基础视角从底栏点击「一键体检」锚点并跑完
2. 切到测试 → Ping 并跑完
3. 回到基础视角 → 页面滚动到「一键体检」区块，结果仍在
4. 进入站点延迟 → 常用官网，分别测试两张卡片
5. 切到测试 → Ping，再回到站点延迟 → 常用官网 → 两张卡片结果仍在
6. 点击「测试全部」→ 旧结果按本包清除，新样本逐张出现；取消时已完成卡片结果保留
7. 在基础视角从「概览」连续手动滚动经过「一键体检」到「上不了网」，确认底栏依次跟随高亮且视口不跳回最初的「概览」；切走再回来 → 恢复到最后选中的「上不了网」区块。该区块同时显示整体诊断、IPv6、MTU 与公网出口细项。
8. 在「建议」或「报告」区点击「查看体检」→ 滚动到「一键体检」并将键盘焦点移到目标区块。
9. 离开整个 feature 再进入 → 恢复上次 `l1Id`（若采用 session 记忆）

### 期望

- 符合 design §3.1 导航记忆表；基础视角 L2 锚点与滚动位置保持同步
- 键盘激活锚点或区块内快捷跳转后，焦点与视口均进入目标区块
- 切换导航**不**清空各面板最近结果（除非用户清除或新跑覆盖）
- 官方站点单卡结果在 L1/L2 导航往返后保留；单卡重测只替换目标卡，整包重测只清理该包目标
- L2 从树中移除后回退到该 L1 第一个合法项

## S-X-02 · 命令透明（hover + 日志）

### 背景

开发者想确认按钮实际调用的 IPC。

### 步骤

1. hover 或键盘聚焦「开始体检」/「Ping」等按钮及一个官网单卡 → Tooltip 显示 IPC 契约名和关键参数
2. 单测官网卡片后打开命令日志 → 见实际 command/event 序列与单卡目标；对任一探测执行一次成功和一次失败，确认日志追加对应终态摘要
3. 展开某个体检项 → 见 `commandHint`；合成项标明非独立 IPC
4. 输入带 userinfo、敏感路径、query 或 fragment 的自定义探测 URL，再检查命令提示 / 日志只显示 origin 与脱敏占位；对 Globalping 与 agent 的拒绝输入也确认日志不含原值

### 期望

- 显示契约名（不翻译标识符）；参数脱敏
- 官网单卡提示包含 `startSitesProbe` 和该卡片目标
- 探测 / 修复命令在调用后追加成功、失败、取消或取消请求已受理的摘要，不把请求已受理误报为任务已取消
- 自定义探测 URL 的凭据、路径、query、fragment 不进入 `commandHint`、样本 target、最终 URL 展示或错误文本；失败输入不得原样进入命令日志
- 降级路径写明 `// degraded: …`
- 无 token/密钥进日志

### 档位

MVP（design §3.5）

## S-X-03 · 高危重置网络栈三次确认

### 背景

用户尝试「一键修复 → 重置网络栈」。

### 步骤

1. 打开修复面板 → 选择 `resetNetworkStack`
2. 走完三步：影响说明 → 参数/后果 → 勾选或确认词；确认期间服务选择、DNS 预设、刷新和其他修复入口均锁定，最终执行的服务 / DNS 值与第 2 步展示的快照一致
3. 让网络服务列表更新并移除已确认的服务，确认当前确认流程关闭，必须重新选择服务并重新开始确认
4. 在第 2 步取消；再次进入须从头
5. 完成执行后后端复核；重复执行幂等

对照：

- `flushDns`：单次确认即可
- `switchDns` / `renewDhcp`：≥两步

### 期望

- 三步状态机，而非三个无关联 Alert
- 前端「confirmed=true」不能绕过后端校验
- 后端在任何副作用前校验一次服务白名单，并在 DHCP 阶段复用已校验的服务；不得在 DNS 刷新后重新读取服务列表
- DNS 刷新与 DHCP 续租有部分成功时，结果仍明确显示两步的结构化反馈
- 每次调用均独立校验；重复执行不依赖上次调用的内存状态

## S-X-04 · 无特权 / 本地网络权限降级

### 背景

标准用户、未授「本地网络」、无 admin。

### 步骤

1. `getNetworkProbeCapabilities()` 记录 privilege 与各 tool 状态
2. Ping 局域网主机、Traceroute、局域网邻居发现（当前降级实现会连接探测 TCP 80/443/22）
3. 观察 UI 灰显与文案；引导系统设置隐私项
4. Ping 样本为 `permission_denied` 时打开权限入口，确认进入“隐私与安全性”；普通超时不提供该入口

### 期望

- 矩阵驱动，禁止硬编码全绿
- traceroute 无特权不假装成功
- Ping 失败时提示本地网络权限可能性（不误报为「网络已断」唯一结论）
- Local Network 权限拒绝时，邻居发现将停止后续 TCP 探测、保留系统缓存结果并显示权限提示
- ICMP socket 初始化失败时显示本地化权限说明，并提供打开“系统设置 → 隐私与安全性”的入口；Ping 单包为 `permission_denied` 时显示相同入口，普通超时不显示权限操作
- macOS Local Network 使用说明随应用 Info.plist 提供中英文版本；用户自行进入“本地网络”检查 Bench 授权
- HTTP/TCP/DNS 等免特权路径仍可用

### 档位

MVP（Post 能力同理标 `U`/`D`/`missing_pack`）

## S-X-05 · 可选能力包安装与卸载（D-017）

### 背景

用户安装后又想卸载 `pcap-diag`，保持主包轻量。

### 步骤

1. 触发缺包功能 → 安装向导
2. 校验失败（后端返回真实 hash 错误或开发验证通道）→ 对话框显示本地化失败状态，原始诊断默认收起，能力包仍为未安装且不执行二进制
3. 安装成功 → 功能可用
4. 「管理组件」卸载 → capabilities 回到 `missing_pack`
5. 确认 MVP 工具（体检/Ping）**从不**走安装墙

### 期望

- `installCapabilityPack(packId)` 无 URL 参数
- Gatekeeper/ad-hoc 提示符合 D-010
- 与 app-manager 更新安全同级：canonical manifest
- 失败反馈必须区分 `hash-mismatch` 与普通失败；关闭并重开管理对话框后不残留旧结果
- 哈希失败测试按钮仅开发构建或显式 QA 构建可见，普通发布构建不显示

### 档位

Post-MVP-Adv

## S-X-07 · 与 port-manager / diagnostics 边界

### 背景

同一主机既要看「本机谁占用了 8080」，又要看「局域网 NAS 的 22 是否开」。

### 步骤

1. 在 **port-manager**：扫本机端口，见 PID，可 Kill（二次确认）
2. 在 **network-probe**：对 NAS `:22` 做 TCP/端口存活；确认无 Kill
3. 从旧 diagnostics / system-settings ping 入口进入：应跳转或薄封装到 `net_probe`，非第二套算法

### 期望

- 占用/Kill ≠ 外部存活探测
- 禁止长期双份 ping 实现（design §13）

## S-X-12 · 单次探测失败重跑不保留旧结果

### 背景

用户连续运行单次探测时，失败的后续请求不能让第一次成功结果冒充当前结果；这也适用于离线诊断整组结果，以及安全、发现面板中的结果卡。

### 步骤

1. Ping `127.0.0.1` 一次并确认成功结果，再将目标改为 `-bad` 并重跑
2. DNS 查询 `example.com` 的 A 记录并确认成功结果，再将域名改为 `-bad` 并重跑
3. TCP 连接一个可达的本机 host:port 并确认成功结果，再将主机改为 `-bad` 并重跑
4. 用可达 URL 运行自定义目标探测并确认成功结果，再将目标改为 `-bad` 并重跑
5. MTU 探测 `127.0.0.1` 并确认成功结果，再将目标改为 `-bad` 并重跑
6. 查询公网 IP 并确认结果，再触发一次失败的公网 IP 刷新
7. 跑成功一轮「上不了网」完整诊断，再让任一子请求失败并重跑
8. 在多节点 DNS 对比中先显示结果，再触发一次受控失败；确认旧答案卡消失
9. 对污染检测、WHOIS、DNSSEC、NAT、NTP、ARP 发现、局域网服务浏览和抓包诊断，分别运行成功一次，再触发失败重跑
10. 查看错误反馈与结果卡；修正输入或条件后确认探测可再次运行

### 期望

- 新 Ping、TCP、DNS、自定义目标或 MTU 请求开始时清除对应的上一轮结果
- 新公网 IP 刷新开始时清除旧 IP；完整离线诊断开始时一并清除 Captive、公网 IP、代理/VPN、IPv6 和 MTU 的上一轮结果
- 污染检测、WHOIS、DNSSEC、NAT、NTP、ARP 发现、局域网服务浏览、抓包诊断和多节点 DNS 的新请求开始时清除各自旧结果
- 无效目标显示本轮失败反馈，不保留上一轮成功结果
- 离线诊断任一子请求失败时不显示来自上一轮的卡片，且错误反馈和重试入口仍可见
- 修正目标后可再次成功运行

### 档位

MVP（P0-1 失败态一致性）

## S-X-34 · 一键离线诊断与 IPv6 / MTU 单项检查互斥

### 背景

一键离线诊断与 IPv6 / MTU 单项面板会写入相同结果槽。并行运行时，较晚结束的操作可能覆盖另一轮结果，让用户看到与当前操作不一致的数据。

### 步骤

1. 在基础视角分别启动 IPv6 或 MTU 单项检查尚未结束时，确认「一键诊断」按钮禁用；再从 use-case 入口尝试启动整组诊断，确认冲突调用被拒绝且不额外派发子检查。
2. 启动一键诊断后切换到测试 → MTU，确认独立 MTU 操作在整组诊断结束前保持禁用；直接调用单项 use-case 也应被拒绝。
3. 两种次序均检查：不重复发起冲突操作，原有结果槽不被冲突请求清空或覆盖，运行结束后按钮恢复。
4. 让一个离线子请求立即失败、另一个受控请求保持 pending；确认错误横幅立即出现但重试按钮仍禁用，完成 pending 请求后整组结束并恢复操作。

### 期望

- IPv6 / MTU 单项操作与 `runOfflineDiagnostics` 互斥，保护共享结果槽。
- 按钮禁用态反映独立检查与整组诊断的 loading 状态；页面切换不能绕开 use-case 的冲突保护。
- 一项子请求失败时立即显示错误反馈，同时等待其他请求 settle；整组 loading 不提前释放，失败轮次的部分结果不落 store。
- 公网出口刷新仍与一键诊断通过共享 `loadingOffline` 防重入；IPv6 和 MTU 两个彼此独立的结果槽可分别单项运行。

### 映射

- UI：`OfflinePanel`、`Ipv6Panel`、`MtuPanel`
- 用例：`checkIpv6Stack` / `probePathMtu` / `runOfflineDiagnostics`
- UX：产品规格 §3.4、§13.3
- 设计：design-basic §1

### 档位

MVP（P0-1 重入与结果一致性）

## S-X-35 · 总览聚合刷新等待所有来源收敛

### 背景

总览刷新并发读取网络摘要、防火墙和 hosts 覆盖。如果一个来源先失败，而其他读取仍未结束，提前释放 loading 会允许重复刷新并重叠派发旧请求。

### 步骤

1. 让防火墙查询立即失败，同时保持网络摘要和 hosts 请求为 pending。
2. 确认错误横幅立即显示，刷新操作仍处于 loading；再触发第二次刷新，确认三个来源都没有重复调用。
3. 让两个 pending 请求结束，确认刷新按钮恢复，概览不会写入失败轮次的部分结果。

### 期望

- 任一来源失败立即显示错误反馈；仍保持 `loadingSummary` 直到全部来源 settle。
- 运行期间的第二次刷新被 use-case 防重入保护拒绝。
- 失败轮次保持原有快照，不将成功子项与失败状态混合写入。

### 映射

- UI：`OverviewPanel`
- 用例：`refreshOverview`
- UX：产品规格 §3 全局交互与反馈、§13.3

### 档位

MVP（P0-1 重入与错误反馈）

## S-X-36 · 能力包刷新 single-flight 与失败反馈

### 背景

能力包列表与 capability 状态需要并发刷新；某个来源先失败时，另一个仍在等待的请求不能被新一轮刷新重叠执行。

### 步骤

1. 让 capability 查询立即失败，同时让能力包列表查询保持 pending。
2. 确认错误立即显示、对话框刷新及安装按钮禁用；再次调用刷新 use-case，确认没有第二组 IPC 请求。
3. 完成 pending 的列表查询，确认 loading 结束且失败轮次没有部分结果写入 store。
4. 在 bootstrap capability / pack 查询尚未结束时分别执行成功、失败的手动刷新，再让旧 bootstrap 返回；确认旧快照不会覆盖当前快照，也不会清除手动刷新错误。
5. 重新刷新并让两个来源都成功，确认列表和 capability 状态一起更新。

### 期望

- `refreshCapabilityPacks` 用例入口以 `loadingCapabilityPacks` 拒绝重复调用。
- 任一来源失败时立即显示错误，但所有来源 settle 前保持 loading 和按钮禁用。
- 只有两个来源都成功时才同时写入能力包与 capability 快照。
- 手动刷新开始时即推进快照修订号；晚返回的 bootstrap 快照不能覆盖刷新前状态，即使刷新失败也不能把错误状态改写成陈旧数据。
- bootstrap 成功只清理 bootstrap / 节点注册表自身的错误，不清除其他操作的错误。

### 映射

- UI：`PackInstallDialog`
- 用例：`refreshCapabilityPacks`
- UX：产品规格 §8、§13.3

### 档位

MVP（P0-1 重入与错误反馈）

## S-X-33 · 持续站点监控、阈值通知与恢复去重

### 前置

### 步骤

1. 输入超过 2048 UTF-8 字节的自定义目标，确认显示双语内联错误且「添加」禁用；再添加 `HTTPS://EXAMPLE.com` 与 `https://example.com/`，确认规范化后只出现一个站点。填满 24 项后再输入一项，确认「添加」禁用且提示先移除站点；删除一项后添加成功。只选择其中 1–3 项开始监控，确认立即采样的 IPC 只包含已选目标，未选站点不探测，目标选择与新增 / 删除控件锁定。

### 期望

## S-X-30 · ARP 发现范围、状态与来源对用户可读

### 背景

ARP 发现依赖系统接口信息和邻居缓存；VPN、多网卡、非私网地址以及不同平台权限状态都可能改变安全范围和可操作入口。结果不能把内部枚举或平台专属操作误呈现给用户。

### 步骤

1. 在中英文界面分别检查 ARP 面板的运行说明、系统缓存模式、缓存 + TCP 模式、TCP-only 模式、结果来源和命令详情。
2. 返回无歧义接口缺失、VPN 接口歧义、大于 `/24` 网段、私有 `/32` 主机路由、同一接口有多个 IPv4 地址和非 RFC 1918 范围结果，确认仅显示对应本地化状态并保留可归属缓存。
3. 检查非 RFC 1918 子网（例如 `169.254.0.0/24`）：不得发起 TCP 主动探测；仅显示同一已选接口和子网的缓存条目。
4. 在 macOS 运行时检查权限拒绝引导；在其他平台确认不显示 macOS 专用 Local Network 设置按钮。
5. 在 Windows 真机分别检查 `GetIpNetTable2(AF_INET)` 返回非空表、`ERROR_NOT_FOUND` 空表、接口索引无法映射和 API 错误；确认空表仍显示缓存 + TCP 模式，API 错误降级为 TCP-only 且扫描继续。
6. 在接口识别 / 系统缓存预检期间点击取消，并在无接口或范围跳过条件下检查结果；确认结果标记取消且会话清理后可立即重跑。

### 期望

- 只对可唯一确认且含其他主机地址的 RFC 1918 私网 `/24` 或更小范围发起 TCP 80/443/22；大网段、无同网段主机、非私网或接口歧义均不主动探测。
- 不把无接口、接口歧义或无权限错误误报成安静网络；不同子网 / 接口的缓存不混入当前结果；TCP 探测排除所选接口上的全部本机 IPv4 地址。

- macOS 与 Windows 成功读取邻居缓存时都如实显示系统缓存来源；空表与读取失败可区分，读取失败降级到 TCP-only / 未执行探测，范围跳过文案不得声称存在缓存结果。
- macOS 可显示本地网络隐私入口；其他平台不显示 macOS 专用入口。
- Windows `GetIpNetTable2` 运行时场景待 Windows 真机验收。
- 接口 / 缓存预检阶段和无接口 / 范围跳过早退均保留取消状态；会话在正常结束和错误退出时清理。
