Bench 2.0 插件化目标 · 可行性评估看板

评估对象：docs/plugin-architecture.md（新增 202 行） + DECISIONS.md D-022　·　 日期：2026-09-08　·　方法：仓库实读核验 + 三路并行行业调研
核心结论

技术方案大体可行，但建立在一个已被推翻的技术前提上；真正的风险不在技术，而在"这个产品是否真的需要插件市场"这一尚未回答的问题。

设计文档把「Tauri 运行时不能热载整屏 UI」当作核心约束，而该约束不成立——项目自身已启用 protocol-asset。前提纠正后，方案性价比排序反转：前端 bundle 插件（uTools 范式）明显优于 WASM 逻辑插件（Zed/Lapce 范式），因为 Bench 的 16 个模块 90% 的工作量是 UI 而非逻辑。

二、技术论断事实核查

不成立　「运行时不能热载全新的 renderer 整屏页面」
文档原文：「Tauri 的 WebView 是静态打包，运行时不能热载新的 renderer 页面……不能自由下载到一个全新整屏页面」
  • Tauri v2 register_uri_scheme_protocol：handler 是 Rust 闭包，可从磁盘任意路径（含 app data dir）读取 HTML/JS/CSS 作为 HTTP Response 返回。协议构建期注册，但 handler 读取的是运行时文件——"注册期静态、内容动态"。
  • asset protocol：配置 scope:["$APPDATA/**"] 即可访问运行时下载的前端 bundle。
  • 社区实证：keathmilligan/tauri-dynamic 运行时从磁盘加载插件 UI（manifest + main.js），dynamic import + blob URL，无需重启。
  • 本项目自身：Cargo.toml 已启用 protocol-asset，tauri.conf.json 已 enable: true——路径已铺了一半。
影响：整个 B-lite 路线的核心取舍依据失效，方案空间重新打开。两个具体阻塞点：① assetProtocol.scope 需从 [] 改为 ["$APPDATA/**"]；② CSP script-src 'self' 未含 asset: http://asset.localhost，插件 JS 会被直接拦截。
机制误用　「插件经 sidecar 交付」
Tauri sidecar 的二进制必须在 tauri.conf.json 的 externalBin 构建期声明并打进 bundle；构建期未声明的二进制无法用 sidecar API 运行。
运行时下载的二进制须改用 shell plugin 的 Command 按绝对路径执行，并配置 shell:allow-execute ACL 与参数 validator。文档 §2.1 未区分这两者，实现时会撞墙。
术语冲突　「plugin」在 Tauri 语境下是编译期概念
Tauri 官方定义 plugin = Cargo crate + 可选 NPM 包，.plugin(init()) 构建期注册、"compiled into the application at build time"。项目已有 tauri-plugin-dialog/-shell/-store 等编译期插件，再引入"运行时 plugin"将持续混淆（对 AI 尤甚，.cursorrules 第 9 条明令禁止自行推断技术栈）。
建议改用独立术语：extension / addon / 能力包。

四、行业调研 A · 同技术栈（Rust + WASM）

项目 插件形态 / runtime 宿主 API 模型 分发与安全 插件能否贡献 UI 生态规模
Zed WASM (wasip2) · wasmtime WIT + wit_bindgen；extension.toml capability + CapabilityGranter 官方 registry + schema_version 门控 ❌ 仅 LSP/DAP/主题 数百
Lapce WASM/WASI · wasmtime PSP（自定义 JSON-RPC）+ WasiCtx 受限 社区 registry，无完整签名/ACL ❌ 仅主题/LSP 较小
dprint 独立 .wasm 共享线性内存字节交换协议 (Schema v4) HTTPS/npm；WASM 默认无 checksum ❌ 纯 formatter 数十
Extism WASM + 多语言 PDK extism:host/user host functions + 加载期能力门控 allowed_hosts + var 限额；XTP 市场 ❌ 框架层不提供 14+ SDK
Spin WASM Component · wasmtime WASI 0.2 + Component Model + WIT allowed_outbound_hosts ❌ serverless 成熟

决定性洞察：所有纯 WASM 逻辑插件系统都没有出现繁荣的第三方生态，插件一律不能贡献 UI，数量在数十至数百量级，与 VS Code（5 万+）、uTools（3000+）差两个数量级。编辑器的插件主要贡献语言能力、UI 需求天然弱；而 Bench 的模块 90% 是 UI。此外，若坚持 WASM 路线，不应自研 ABI——Extism 或 WIT 二选一即可省掉全部多语言 SDK 成本。

五、行业调研 B · 插件市场型应用范式

案例 宿主 插件形态 UI 呈现 沙箱 生态规模
uTools Electron plugin.json + index.html + preload.js ✅ 整屏自由 无 3000+
Rubick Electron 同 uTools（API 对齐 90%+） ✅ 整屏 无 npm 源
VS Code Electron package.json contributes + Node 模块 ✅ 声明式贡献点 ✅ 进程级 5 万+
Raycast 原生 macOS TypeScript/React npm 包 受控组件，非任意 DOM ✅ 线程级 数千
Figma Web sandbox JS + iframe UI iframe 模态 ✅ iframe 数千
Obsidian Electron main.js + manifest.json 受控注入贡献点 默认全信任 数千

规律 1：成功的插件市场，插件一定能贡献 UI——要么整屏自由渲染，要么声明式注入宿主壳。没有任何繁荣生态是"插件只贡献纯逻辑"。
规律 2：形态与产品性质强相关。工具箱/效率平台（uTools、Rubick、Raycast）→ 前端插件 + UI；编辑器 → 进程/WASM + 语言能力。Bench 属于第一类，同构参照是 uTools 而非 Zed。
规律 3（Figma 教训）：Figma 从纯 iframe → JS 解释器 WASM → 主线程沙箱 + iframe UI，两次返工才定型，并明确否掉了「WASM 跑逻辑 + 预置壳渲染 UI」这一组合——而这正是 B-lite 的设计。

六、产品可行性：一个必须回答但尚未回答的问题

目标 A · 降低自己的装配成本

  • 痛点：加一个能力要改 registry.tsx + commands.rs + lib.rs 三处
  • 正解：约定式注册 + 代码生成（inventory/linkme crate 自动收集命令、import.meta.glob 自动装配）
  • 成本：1–2 天，零运行时风险

目标 B · 建立第三方插件生态

  • 痛点：外部开发者能为其扩展能力
  • 正解：manifest + 沙箱 + 签名 + registry + SDK + 文档 + 审核流程
  • 成本：数月 + 持续运营，需完整信任模型，生态冷启动是最大不确定性

文档 §0 的第一条目标原文是目标 A 的表述（"把新增能力要在 3 处手写装配收敛为能力自带契约"），但整份文档给出的是目标 B 的方案。两者成本差两个数量级，被混为一谈了。
冷静观察：Bench 的 16 个模块高度个人化、强系统耦合，多数涉及双平台专有 API 与权限，第三方作者池极窄（需同时懂 Rust + Tauri + 双平台系统 API）。对照 uTools——其 3000+ 生态建立在前端开发者零门槛之上。建议投入架构前先写下"第一个第三方插件作者是谁、他要写什么"。

七、建议方案：B′（宿主 + 可下载前端 bundle）

B-lite（原设计）

  • 插件主体：WASM / sidecar / 远程
  • UI：❌ 预置壳或远程视图
  • Rust 宿主：内嵌 wasmtime（Windows 编译风险）
  • 宿主 API：自研 bench_host WASM 导入面
  • 签名：新设计
  • 作者门槛：需会 Rust/WASM

B′（建议）

  • 插件主体：前端 bundle（React）+ 可选 WASM 附属
  • UI：✅ 独立 WebView 整屏渲染（asset/自定义协议）
  • Rust 宿主：不引入 WASM runtime，复用既有 IPC
  • 宿主 API：IPC 命令白名单网关（复用契约双写体系）
  • 签名：复用已有 minisign 密钥链
  • 作者门槛：前端开发者零门槛
  • + 声明式 contribution points（抄 VS Code / Obsidian）

风险与对策：① 信任边界扩大 → 三道闸门（assetProtocol scope 限定 $APPDATA/plugins/**／CSP 精确放行／Rust 侧 manifest.acl 命令白名单网关）；② 插件崩溃 → 独立 WebView 进程级隔离 + 自动停用；③ API 演进破坏插件 → 版本化 API + engines 兼容声明；④ Figma 教训 → 先做受限版，预留收紧空间，不做不可逆宽授权。

八、修订后的分阶段路线

P0 · 产品定案
回答目标 A 还是目标 B；写下第一个第三方插件作者画像。若选 A → 走轻量路径，其余阶段作废 决策点
P1 · 概念验证（1–2 天）
不改架构，仅验证 asset 协议 + CSP 放开后能否加载 $APPDATA 下的 React bundle。这一步决定 B′ 是否成立 低风险
P2 · 契约先行
manifest schema + contribution points 枚举 + ACL 命令白名单 + minisign 校验骨架 中
P3 · 单插件闭环
选 1 个低风险模块（建议 token-calculator）走完整路径：打包→安装→隔离渲染→白名单调用→卸载 中
P4 · 插件中心 UI
目录 / 安装 / 启用禁用 / 卸载 + 能力矩阵 中
P5 · 泛化与迁移
dev-toolbox host 泛化；按 253 条命令实际基数分批迁移 高
P6 · Windows 复验
恢复 Windows CI（撤销 D-021 暂停部分），验证插件子系统双平台可用——硬前置，否则等于发布单平台未验证能力 高
