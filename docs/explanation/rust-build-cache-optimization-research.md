# Rust 构建缓存与构建内存优化 — 调研报告

> **状态**：调研方案已实施；§1 的体积基线为 2026-09-10 历史记录，最新清理结果见 §8。
> **日期**：2026-09-10
> **关联**：D-021（target 目录外迁 + sccache）、clean-space 模块规划、后端构建高内存占用 backlog
> **TL;DR**：target 目录已达 **27GB**（debug 占 25GB），根因是 `debug=2` 全量调试信息 + 增量缓存历史会话堆积 + Cargo 从不清理陈旧产物。**P0 两项改动（profile 调优 + 一次性清理）预计把常态水位压到 8-10GB，编译内存峰值降约 30%**，代价仅为依赖库内部失去断点调试能力。

## 2. 根因分析

**磁盘三类根因（按贡献排序）：**

1. **`debug=2` 全量调试信息**：Cargo dev profile 默认生成完整调试信息并编入 rlib/rmeta/.o 与最终二进制。objc2 系（app-kit/foundation/web-kit）宏展开代码量巨大，放大最明显。deps 17 GB 的主要构成。
2. **增量缓存无 GC**：Cargo 按会话组织 incremental 目录，代码/依赖图变更后旧会话目录**不会被主动清理**（`cargo gc` 仍是实验特性），6 个历史会话堆积 7.5 GB。
3. **陈旧产物**：依赖图每次变化产生新 hash 的二进制/rlib，旧副本永不清理（上面 4+ 份 bench 二进制、objc2 两份版本即证据）。

**构建内存三类根因：**

1. rustc 全程携带完整调试元数据（MIR → LLVM IR → 机器码），debuginfo 生成是编译期内存大户之一。
2. 最终链接 808 MB staticlib，链接器峰值内存高。
3. release 全量 LTO（`lto = true`）——低频触发，但峰值最高。

## 3. 方案矩阵

| #   | 方案                                                                                                                | 磁盘收益                                                | 内存/速度收益                                                   | 代价与风险                                                                                         | 级别       |
| --- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------- |
| A   | **`[profile.dev]` 调优**：`debug = "line-tables-only"` + 依赖包 `debug = false`                                     | deps 17 GB → **约 5-7 GB**；二进制 105 MB → 约 60-70 MB | rustc 内存峰值 **-30% 左右（估算）**；链接更快；CI 磁盘同步受益 | 依赖库内部无法断点/无符号（**自己代码行号保留**，栈回溯可读）；改动触发一次全量重编译（约 10 min） | **P0**     |
| B   | **一次性整理**：incremental + 陈旧 hash 产物移入废纸篓/回收站，保留最新副本                                         | 历史估算可整理体量约 **8 GB+**；移入后不会立即释放      | 无                                                              | 可恢复；清空系统废纸篓/回收站后才释放磁盘空间                                                      | **P0**     |
| C   | **自动清理脚本**：`scripts/maintenance/rust-cache-clean.mjs`（依赖成熟的 `trash` 包），注册进 menu.mjs              | 长效整理旧产物（保留期限内的 incremental/陈旧产物不动） | 无                                                              | 只移入系统废纸篓/回收站，可恢复；**清空后才释放磁盘空间**                                          | **P1**     |
| D   | **sccache 缓存上限**：`SCCACHE_CACHE_SIZE="5G"`（写入 config 或 launchd）                                           | 防缓存无限膨胀（现 2.2 GB）                             | 无                                                              | 无实质风险                                                                                         | **P1**     |
| E   | **链接器换 lld**：`brew install llvm` + `[target.aarch64-apple-darwin] rustflags = ["-C", "link-arg=-fuse-ld=lld"]` | 无                                                      | 大体积链接峰值内存更低、速度更快                                | macOS 上 lld 偶有链接兼容性坑，需验证 .app 正常运行                                                | P2（可选） |
| F   | **release 改 `lto = "thin"`**                                                                                       | 无                                                      | release 构建内存/时长显著下降，二进制略增                       | 发布产物体积 +5-10%；仅当 release 构建确实卡内存时启用                                             | P2（可选） |

> 说明：A 是官方文档明确支持的做法（`line-tables-only` 以极小代价保留栈回溯行号）；profile 与 `#[cfg]`/平台分支无关，**不触发 `check:be-cfg` 门禁**，Windows 侧同样受益。

## 4. 推荐组合与实施步骤

### Phase 1 — 立即（P0，改动两个文件 + 一条命令）

1. `src-tauri/Cargo.toml` 增加：

   ```toml
   [profile.dev]
   debug = "line-tables-only"   # 自己的代码保留行号，栈回溯/断点仍可用

   [profile.dev.package."*"]
   debug = false                # 依赖库不生成调试信息（objc2 系是膨胀大头）
   ```

2. 一次性整理（温和方案；先预览）：

   ```bash
   pnpm run clean:rust-cache --sweep --dry-run
   pnpm run clean:rust-cache --sweep
   ```

3. 重编译一次（fingerprint 失效属预期，约 10 min），验证 dev/test 正常。

### Phase 2 — 短期（P1，落地自动清理机制）

4. 新增 `scripts/maintenance/rust-cache-clean.mjs`：
   - `--stats`：统计 target 各子目录占用
   - `--sweep [--older-than 7d]`：将超龄 incremental 会话 + 同名多 hash 陈旧二进制移入系统废纸篓（保留最新副本）
   - `--dry-run`：预览候选项；移入失败则保留原文件，不会退回永久删除
   - 使用 `trash` 包调用各平台系统废纸篓；菜单和 CLI 都显示“移入废纸篓后不会立即释放空间”
5. sccache 设 `SCCACHE_CACHE_SIZE="5G"` 上限。
6. 按约定回写 `docs/explanation/decisions.md`（新 D-xxx：构建缓存治理策略）。

### Phase 3 — 可选（P2，按需评估）

7. lld 链接器 / release thin LTO：出现实际痛点（链接 OOM、release 构建过慢）时再启用。

## 6. 风险与回滚

| 风险                   | 影响                                     | 缓解/回滚                                                                     |
| ---------------------- | ---------------------------------------- | ----------------------------------------------------------------------------- |
| 依赖库失去调试信息     | 无法在依赖库内部断点、依赖帧栈回溯无行号 | **回滚 = 删两段 toml 配置**，重编译即恢复；自己代码的调试能力不受影响         |
| 全量重编译一次         | 约 10 min 一次性成本                     | 与全量依赖升级成本相当，可接受                                                |
| 清理脚本移入误判的产物 | 下次构建强制重编                         | 策略保守（超龄 + 保留最新副本）；文件仍在系统废纸篓，可恢复；失败时源文件保留 |
| lld 兼容性（P2）       | 链接失败/运行异常                        | P2 默认不启用，启用前单独验证                                                 |

## 7. 初始待确认决策点（历史）

1. **是否接受「依赖库无调试信息」**（方案 A 核心取舍）——推荐接受，日常调试对象是自己代码。
2. **一次性整理力度**：温和（移入 incremental + 陈旧产物，保留最新副本）——不提供永久全清入口，避免误删共享构建缓存。
3. **自动清理脚本归属**：按 clean-space 模块集成（推荐，符合既定架构）还是纯 CLI 独立使用。
4. **是否顺带设定 sccache 上限**（推荐 5 GB）。

以上决策已在 §8 记录实施结果；本节保留作历史背景。

日常建议：

- 别手动清理 `debug/build/`（build script 产物，删掉要重编译 `aws-lc-sys` 等 C 依赖，极慢）；
- 先跑 `pnpm run clean:rust-cache --sweep --dry-run` 检查候选项，再运行 `pnpm run clean:rust-cache --sweep`；默认保留 7 天内产物并要求确认；
- `pnpm run clean:be` 是上述可恢复整理的别名，不会执行 `cargo clean`；
- `pnpm run clean` 只会把仓库内 `dist/` 和旧位置 `src-tauri/target/` 移入废纸篓，不会清理共享 target 或 `node_modules`；
- `--include rust-analyzer` 会把 IDE check 产物移入废纸篓（约 1.9 GB，可重建），建议先关闭 IDE；
- 移入废纸篓/回收站不会立即释放磁盘空间；要释放空间需用户之后在系统中清空废纸篓/回收站。
