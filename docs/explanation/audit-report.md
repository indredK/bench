- [后端 / 网络结果可信度与协议安全] `src-tauri/src/net_probe/nat.rs` — **Risk:** 远程 main 的手写 STUN 解析没有校验 UDP 响应源地址或事务 ID，且事务 ID 由时间戳生成；迟到、无关或伪造的数据报可能被误当成当前服务器映射结果。socket 固定为 IPv4，解析到 IPv6 的服务端会失败；多服务器映射不同时还输出 `symmetric-or-varied`，容易把服务器差异误读为 NAT 类型。**Severity: Medium.** **Refactor:** 当前工作区已采用 `rtc-stun` 的 STUN 消息编解码与随机事务 ID，按源 endpoint 和事务 ID 过滤响应，支持 IPv4/IPv6 并保留有界 DNS 地址故障转移；输出逐源映射观察，不把跨服务器差异称作 symmetric NAT。**Philosophy:** 协议库负责容易出错的二进制边界，应用只保留产品特有的分类编排；网络观察与 NAT 推断明确分层，避免把错误响应或不同观察条件包装成确定结论。Rust 专项测试、此前全量门禁和依赖审计通过；2026-10-25 隔离 macOS 真机对 Google 两个固定 STUN endpoint 查询超时，Cloudflare endpoint 返回映射地址；界面只显示“类型未知”并说明单个来源不足以判断，符合保守判定。RFC 5780 映射 / 过滤行为分类仍未实现；PR #108 的旧 head 有协议步骤与聚合限速缺陷且与主干文件冲突，不能直接合并。

- [PR 审计 / RFC 5780 正确性与速率限制] [PR #108](https://github.com/indredK/bench/pull/108) 的 `src-tauri/src/net_probe/nat_behavior.rs` — **Risk:** 过滤行为 Test III 应向主 endpoint 发送带 `CHANGE-REQUEST(change-port)` 的 Binding Request；当前代码却对 alternate-address / primary-port 发送普通 Binding Request，并把它同时当作过滤 Test III 与映射 Test II，结果可能错误分类过滤行为。另外，每个配置服务器各自使用 100ms pacing，但 `join_all` 并发探测最多 3 个服务器，进程内甚至跨并发 IPC 调用没有聚合限速，可能超过 RFC 5780 每客户端每秒 10 个新事务的建议并同时扰动 NAT 状态。**Severity: Medium.** **Refactor:** 分别实现正确的过滤 Test III 和映射 Test II；回归验证每一阶段的目标地址、`CHANGE-REQUEST` 位、期望响应来源与映射结果；使用共享的进程级调度器聚合限速，并顺序运行多源端口发现。**Philosophy:** 测试步骤必须与 RFC 中的不同观测条件一一对应；速率限制要覆盖全部并发请求，避免“单任务合规、总流量超限”。PR #108 的测试覆盖了独立编码 / 分类 helper，但未端到端断言完整发现序列各阶段的目的地址、属性与响应来源；旧 head GitHub checks 全绿，但此实现缺陷与当前主干文件冲突必须先修复，不能依 CI 绿灯合并。依据 [RFC 5780 §4.4](https://www.rfc-editor.org/rfc/rfc5780.html#section-4.4) 与 [§5](https://www.rfc-editor.org/rfc/rfc5780.html#section-5)。
